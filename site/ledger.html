The ledger — what a real Ring page costs

A working data page, with its logic written in Ring and running in your browser: twenty thousand deposits you can filter, sort, total and add to. It exists to answer one question honestly — and it found two bugs in the Ring VM while doing so.

Open the ledger ↗ Read the full write-up ↗

The question is not "is Ring faster than JavaScript"

That comparison is easy to rig, hard to make fair, and answers nothing a page author actually needs. This asks something narrower and more useful:

If you write an ordinary data-driven page in Ring, does it feel right to use?

"Feels right" is not an opinion here. It is three thresholds that come from how people perceive delay, and they do not care which language you picked:

  • instant< 16 ms inside one animation frame — the result is simply there
  • responsive< 100 ms feels caused by the click
  • noticeable> 100 ms the page is visibly thinking

Every interaction is measured against those, and labelled. JavaScript is on the page, but only as a referee: it recomputes every answer from the same data and marks it correct or not. It has no timing column, because "is Ring correct" is the question worth asking of it.

The data lives inside the VM

That is the whole reason a resident runtime exists. The ledger is loaded once, into Ring globals held as columns, and every later interaction works on that copy. Nothing crosses the bridge again except the answer — no re-parsing, no re-sending, no JSON per keystroke.

What it costs

Interaction20,000 rows50,000 rows
Draw a page of 25 rows0.2 ms0.4 ms
Recompute the totals11 ms28 ms
Filter, on every keystroke15 ms38 ms
Sort a column53 ms130 ms
Rebuild the leaderboard92 ms238 ms
Load, once at startup106 ms879 ms

At twenty thousand rows, everything a user touches is instant or responsive. At fifty thousand, two interactions cross the line — and the page says so rather than hiding it.

But those are the numbers after the app was driven like a real one. On its first run, totalling fifty thousand rows took 5.7 seconds and the leaderboard took nearly twenty.

What driving it found

Sorting by a column was quadratic VM bug, fixed

Ring's sort rebuilds the list by reading it in sorted — that is, random — order. Without an index array, every read walks the list. Sorting twenty thousand rows took 257 ms, quadrupling each time the data doubled. Building the array first: 16 ms.

Random list access walked the list, every time VM bug, fixed

The deeper one. Ring's list cache is a cursor: sequential access is instant, random access falls through to a linear walk and is never remembered. So any pass over a big list through a sorted index — "sort the table, then total the visible rows", the most ordinary thing a data page does — was O(n²). Totalling fifty thousand rows went from 5,751 ms to 31 ms; the leaderboard from 19.8 s to 277 ms.

Ask your API for rows, not objects no VM change

Loading fifty thousand deposits took 7.9 seconds — and almost none of it was parsing. A JSON object becomes a pair-list in Ring: a list per field, two items per field. Twenty thousand five-field records were taking 88 MB, and most of that second was spent first-touching memory the page immediately throws away. Sent as arrays instead — [1,"m03",3,250,"ACTIVE"] — the same data costs 23 MB and loads in a tenth of the time. Load went 7.9 s to 0.88 s.

Five Ring rules, learned by getting them wrong

Functions called from the page take exactly one parameter. Do not name one after a builtin — func Load collides with Ring's own load. Index your loops and hoist the length, because for x in aList hands back a copy of every item. And assignment copies, so o = aList[i] gives you a copy that writes to nothing. They are all at the top of the source, where the next person will meet them before the bug does.

What this proves, and what it does not

It proves the runtime is sound for real data work at real sizes. A twenty-thousand-row page is instant to filter, sort and total, every answer matches JavaScript's, and all ~850 conformance programs still match native Ring byte-for-byte after both VM patches.

It does not prove Ring is as fast as JavaScript — it is not, and that is measured honestly elsewhere. Nor does it speak for half-million-row workloads, which would need a different approach than a linear scan.

The useful claim is narrower and more durable: an ordinary Ring page, at the sizes ordinary pages carry, feels like a page. The way to keep that true is to keep driving real applications — that is what found all four items above.
