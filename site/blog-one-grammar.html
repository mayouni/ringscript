One grammar, three runtimes

Vision & direction August 2026 · Mansour Ayouni

The rules of a savings circle do not change when you move from the server to the browser. So why should they be written twice, in two languages, and drift apart quietly for the rest of the product's life?

The rule that keeps getting rewritten

Every business application has a handful of sentences at its centre. A deposit must bring something to the circle. The collector records; the treasurer audits. Bulk imports still pass every step. These sentences are the product. Everything else is plumbing.

And in most systems they are written at least three times: once in the database as a constraint, once on the server as a validation, once in the page as a form check — three dialects, three places to forget, and a bug report that begins "the web version lets you do it but the app doesn't".

The alternative is to write the sentence once, in a form that is neither server code nor page code, and let every runtime read the same file. That is what ZQL is: a tiny declarative grammar for entities, norms, flows and the one door data may arrive through.

DEFINE ENTITY deposit (
  id: uuid,
  member: text,
  amount: currency,
  round: int,
  status: enum("STAGED", "AUDITED", "ACTIVE")
) RATIONALE "One member contribution to one round of the circle"

DEFINE NORM positive_deposit AS (
  RULE: amount > 0,
  MESSAGE: "A deposit must bring something to the circle"
)

DEFINE FLOW collect (
  STEP 1: RECORD -> { ACTOR: collector,  VALIDATE: member != "" },
  STEP 2: AUDIT  -> { ACTOR: treasurer,  ENFORCING: positive_deposit }
) RATIONALE "The collector records; the treasurer audits"

Note what the MESSAGE is for. It is not a comment: when the norm stops a flow, that exact sentence is what the outcome carries back to whoever is standing at the counter. The rule and the explanation cannot drift apart, because they are the same declaration.

Three engines, one file

The same grammar has three complete implementations, each living where it earns its keep.

The Ring implementation — stzZql.ring, a hand-written tokenizer, recursive-descent parser, expression evaluator and small interpreter in pure core Ring — ships baked inside ringscript.wasm. And the proof that this is not a slide: in the framework's repository, a page loads one app.zql, runs the tontine flow through the JavaScript runtime and through Ring-on-wasm side by side, and compares. Same declaration, identical verdicts.

The surprise: the Ring parser is the small one

A fair question when we chose what to embed: a Zig implementation of the same grammar already existed, self-contained, and would compile straight into the wasm. So we built both and weighed the artifact.

the Ring source, embedded24,253 bytes
the Zig implementation, compiled in43,262 bytes

The Zig version is 19 KB larger, and the reason is structural rather than a quirk of either program. The Ring version is 21.7 KB of source text, and the machine that runs it — tokenizer, parser, evaluator, lists, strings, garbage collector — is already in the binary, because RingScript is the Ring VM. It rides for free. The Zig version must bring its own tokenizer, parser, AST and evaluator.

Inside a binary that already contains a complete language implementation, writing a parser in that language is the cheap option.

Zig would parse far faster. But a page pays the wasm size on every load and the parse cost once, if ever — for the web that trade runs the wrong way. Where the Zig implementation earns its place is where it already lives: the CLI and the engine, running natively, at volume, with no Ring VM nearby to borrow. Three runtimes, three homes.

Why the verb set is closed

There is no DROP in ZQL. No DELETE, no UPDATE. Not because they are blocked, checked, or filtered — because they are not in the grammar, so they cannot be expressed:

StzZqlQ("DROP TABLE users")
# stzZql (line 1): Unknown verb 'DROP'. The ZQL verb set is closed --
# destructive or unrecognized operations are not part of the grammar.

This is a different kind of guarantee from a permission check. A permission check is code that must be correct, kept current, and applied everywhere; a closed grammar is a property of the language, and it holds even when the declaration arrives from somewhere you do not control. It is the property that makes running one of these files inside a browser a reasonable thing to do at all.

The same instinct runs through the runtime underneath it: RingScript has no filesystem to sandbox, because the Ring VM's file layer was redirected at compile time to an embedded, read-only map. Not guarded — absent. The strongest security property is the one you cannot switch off.

What this is really about

A small country office, a school, a cooperative — the places this software is built for — cannot afford a rule that means one thing on the server and another on the counter clerk's screen. They also cannot afford three teams to keep the two in step.

Writing the rule once, in a grammar small enough to read aloud, and having every runtime obey the same file is not an architectural preference. It is how a team of two keeps a system honest for ten years. RingScript's contribution to that is narrow and specific: it made the browser one of the places the Ring implementation can run, so the front of the application stopped being the one place the rules had to be retyped.

The grammar, in full, with every production and the Ring surface that reads it: docs/zql-payload.md. The engine itself: src/ringlib/stzZql.ring, with its ten-assertion suite running inside the wasm as a permanent gate.
