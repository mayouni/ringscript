RingScript compiles the Ring VM to WebAssembly and keeps it alive between evaluations — persistent state, trapped errors, interactive input, and a two-way JSON bridge to JavaScript. No plugins, no server round-trips, no Emscripten.

Your page logic — in Ring, not JavaScript

Put your logic in a <script type="text/ring"> block; buttons call Ring functions directly, and Ring reads and writes the page through the Platform() seam. The demo on the right is running this exact source, live:

The complete page — no JavaScript written by you
<script src="ringscript.js"></script>
<script>RingScript.boot()</script>

<input id="guest" placeholder="Your name">
<button onclick="ring.call('Greet')">Greet</button>
<button onclick="ring.call('AddOne')">+1</button>
<div id="hello"></div>
<div id="n"></div>

<script type="text/ring">
nClicks = 0

func Greet aEv
    cName = Platform(:getvalue, [ :id = "guest" ])
    if cName = "" cName = "stranger" ok
    Platform(:settext, [ :id = "hello",
        :text = "Ahlan, " + cName + "!" ])

func AddOne aEv
    nClicks++
    Platform(:settext, [ :id = "n",
        :text = "clicked " + nClicks + " times" ])
</script>

Deploying — copy two files, that's all
your-site/
├── index.html
├── ringscript.js      ← the loader (~12 KB)
└── ringscript.wasm    ← the Ring VM (~340 KB)
Any static host works — no toolchain, no bundler, no server code. (The zig build serve workflow only concerns programmers changing the runtime itself.)

Resident, not batch

One RingState lives for the whole page. x = 5 in one eval, see x in the next. Errors are trapped with real line numbers and never kill the VM — 1000 evals, flat memory.

Native-exact

~850 programs — Ring's own samples, the documentation examples, and a 24-example gallery — produce output byte-identical to native ring.exe, verified continuously against the real thing.

Two-way JS bridge

ring.call("Fn", {…}) sends JSON in and gets JSON out; Ring's jscall() raises DOM events or invokes your handlers. Embed pure-Ring libraries straight into the wasm.

Embedding it in your own page

JavaScript — the embedding API
const ring = await RingScript.load("ringscript.wasm");
ring.eval('func Double aData return [ :value = aData[:n] * 2 ]');
const r = ring.call("Double", { n: 21 });
// r.result --> { value: 42 }
Why this shape
Keep the page in JavaScript when you want to, and script the logic in Ring: arguments go in as JSON, results come back as JSON, and nothing about your page has to change. The seam is thin, typed by convention, and entirely optional.

One language, both sides of the wire

Ring already speaks server-side: Ring WebLib and the Bolt web framework (Express-style DSL, new in Ring 1.27) build and serve real sites in Ring today. What was missing was the front end — the part browsers only ran JavaScript for. RingScript completes the picture: the same language, the same idioms, from the request handler on the server to the click handler in the page. One team, one grammar, full stack.

Real sites, browser rules

RingScript is built for production front ends — page logic, forms, live business rules — and for playgrounds, notebooks and teaching. It plays by the same rules every web app plays by: inside the browser sandbox there are no files, no OS calls, no threads. Ring programs that ask for them get a clean, trappable Ring error — never a dead runtime — and everything else in the language works exactly as it does natively.

Part of the Softanza Project

RingScript is developed within the Softanza Project, and was made so that Ring can serve as an alternative frontend scripting language in the StzWeb framework — where the same business declaration can be evaluated by StzWeb's JavaScript runtime and by Ring-on-wasm, side by side, with identical verdicts.
